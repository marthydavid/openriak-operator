# Basho Bench

[Basho Bench](https://github.com/OpenRiak/basho_bench) is Riak's own load generator. This page
documents how to build it for OpenShift/OKD, how to drive an mTLS-secured cluster with it, and what a
run shaped like the [soak test](soak-test-results.md) measured. The tooling lives in
[`examples/basho-bench/`](https://github.com/marthydavid/openriak-operator/tree/main/examples/basho-bench).

**Verdict: mTLS works with Basho Bench against Riak 3.2.6, and the soak-shaped run did not reach the soak's
load.** All 10 clients authenticated with their client certificates and ran for 28 minutes without a
container restart or OOM kill, but they achieved 175 ops/s on average against the 600 ops/s the soak test
held, and throughput fell during the run. The reasons are not established (see
[What the shortfall means](#what-the-shortfall-means)).

## Which fork

The original `basho/basho_bench` repository's last commit on its default branch is from 2022. The
OpenRiak organisation keeps a fork,
[`OpenRiak/basho_bench`](https://github.com/OpenRiak/basho_bench), whose `openriak-3.2` branch (last commit
2025-01-13, "OTP 26 compatible deps") depends on the OpenRiak forks of its libraries. This page uses that
branch with Erlang/OTP 26.

## The image

CI builds it from [`images/basho-bench/Dockerfile`](https://github.com/marthydavid/openriak-operator/blob/main/images/basho-bench/Dockerfile)
(workflow `build-basho-bench.yml`) and publishes `ghcr.io/marthydavid/basho-bench:openriak-3.2` (also `latest`
and a short-SHA tag) from `main`; same-repo pull requests push `pr-<N>` only. It is `linux/amd64` only: the
arm64 build of the `eleveldb` and `bitcask` dependencies has not been tried. The Dockerfile pins the fork to
the commit that was tested. `soak-like.py` uses this image by default.

## Building it on OpenShift

[`build.yaml`](https://github.com/marthydavid/openriak-operator/blob/main/examples/basho-bench/build.yaml)
is a `BuildConfig` with the same Dockerfile inline (no git source needed) that pushes to the cluster's internal
registry, for clusters that cannot pull from `ghcr.io`:

```bash
kubectl apply -f examples/basho-bench/build.yaml          # creates the bench namespace and the BuildConfig
kubectl -n bench create --raw /apis/build.openshift.io/v1/namespaces/bench/buildconfigs/basho-bench/instantiate \
  -f - <<< '{"kind":"BuildRequest","apiVersion":"build.openshift.io/v1","metadata":{"name":"basho-bench"}}'
```

The internal image registry must be enabled. Three things the build needs:

- the official `erlang:26` image, which already contains `rebar3`;
- `cmake` and a compiler: the `eleveldb` dependency builds snappy with cmake;
- **a one-line patch**, described next.

### The protobuf driver does not start TLS

The stock `basho_bench_driver_riakc_pb` passes `pb_connect_options` to the Riak client, which accepts the
TLS options (`credentials`, `cacertfile`, `certfile`, `keyfile`), but the driver never starts Erlang's `ssl`
application. Connecting then fails with `{tcp,ssl_not_started}`. With `auto_reconnect` in the options the
failure is **silent**: the workers start, send nothing, and the run reports "No Errors" with zero
operations. `build.yaml` therefore inserts `application:ensure_all_started(ssl)` at the top of the driver's
`new/1` before compiling.

## Configuration

A client's `.config` for mTLS (generated by `soak-like.py`, one file per user):

```erlang
{driver, basho_bench_driver_riakc_pb}.
{riakc_pb_ips, [{"bsoak.bench.svc.cluster.local", 8087}]}.
{riakc_pb_bucket, {<<"bsoak-t00">>, <<"bsoak-b00">>}}.        %% {bucket type, bucket}
{pb_connect_options, [
    {credentials, "bsoak_u00", ""},                           %% the RiakUser's username, empty password
    {cacertfile, "/certs/ca.crt"},
    {certfile, "/certs/tls.crt"},
    {keyfile, "/certs/tls.key"}]}.
```

Do **not** add `auto_reconnect`. The certificate files are the `<riakuser>-client-tls` Secret that the
operator's `RiakUser` produces; mount it at `/certs`. Without a certificate Riak refuses the connection
(`Security is enabled, please STARTTLS first`), which was checked with the same image.

Notes on the driver:

- `{mode, {rate, N}}` is **per worker** and closed-loop: each worker starts its next operation only after
  the previous one finished, so a client with 16 workers at 3.75 ops/s each targets 60 ops/s.
- A bucket type is given as a `{Type, Bucket}` tuple.
- Reads send `r` and writes send `w` (and `dw`); there are no `pr`/`pw` options on the request. The run sets
  `pr` and `pw` as the **bucket defaults** through the `RiakBucket` properties, as the soak test does.

## A run shaped like the soak test

[`soak-like.py`](https://github.com/marthydavid/openriak-operator/blob/main/examples/basho-bench/soak-like.py)
prints the cluster, buckets, users, configs and client Jobs. The soak test's constraints, and what this run
used:

| | Soak test | This run |
|---|---|---|
| Cluster | 3 Riak nodes, 16 GiB memory (request = limit), 4 CPU request, no CPU limit, 300 GiB PVC each | same |
| Riak | 3.2.6, TLS, `ring_size` 128, monitoring on, `n_val` 3, `pr`/`pw` 2 | same |
| Users, buckets | 10 mTLS users, 10 buckets (one bucket type each) | same; each client uses its own bucket |
| Load | 600 ops/s total, 50 % reads, 128 KiB objects, open-loop | 600 ops/s targeted (60 per client), 1:1 get/put, 128 KiB objects, closed-loop |
| Clients | 10 pods, 16 threads each, 250m CPU request | 10 pods, 16 workers each, 250m CPU request, 256 Mi request, 1 Gi limit |
| Keys | 300 per bucket, rotating over all 10 buckets | 3,000 per client, one bucket |
| Duration | 4 h | 28 min (a time limit for this run) |
| Read-back check | every key read back at the end | none; Basho Bench does not read back |

```bash
python3 examples/basho-bench/soak-like.py --duration 28 > soak-like.yaml
kubectl apply -f soak-like.yaml                                  # needs the riak-ca-issuer Issuer, see mtls.md
python3 examples/basho-bench/collect.py run1 30 &                # server-side series, while the clients run
```

Each client prints its per-window latency CSVs when it finishes. Turn them into the soak test's artifact
format and draw the same charts:

```bash
for i in 00 01 02 03 04 05 06 07 08 09; do kubectl -n bench logs job/bsoak-client-$i > logs/client-$i.log; done
python3 examples/basho-bench/to-artifacts.py run1 logs art
python3 hack/soak-report.py art docs/assets/basho-bench
```

`to-artifacts.py` marks the run as passed only for at least 95 % of the target rate, under 0.1 % errors, no
OOM kill and no restart. The overview shows the integrity tile as "not checked".

## What the shortfall means

Facts: the soak test held 600 ops/s on this cluster with the same resource constraints, and its worst-client
p99 had a median of 516 ms (worst 1.9 s). Basho Bench reached 175 ops/s with a median worst-client p99 of
1.7 s (worst 7.7 s), and its throughput fell as its latency rose.
Riak's own get time at p99 reached 60 s in places (the default request timeout), so some reads waited for a
replica.

What follows from that is limited. Closed-loop workers cannot hold a rate once an operation takes longer
than their interval (267 ms here), so the client falls behind and does not catch up; that explains why the
rate follows the latency. It does **not** explain why the latency was higher than under the soak's client,
and this run did not find out. Candidates that were not tested: the number of concurrent connections, how the
Erlang client handles 128 KiB values, the clients competing with Riak for the same three nodes, or the
bucket-type and key layout. Treat the numbers as "Basho Bench with these settings", not as a statement
about the cluster's capacity, which the [soak results](soak-test-results.md) cover. A rerun with more
workers per client, or separate client nodes, would separate those.

## Not covered

One run, 28 minutes, Riak 3.2.6 only; Riak 3.0 and 3.4 were not benchmarked. No integrity check of the
stored values. The HTTP driver (`basho_bench_driver_http_raw`, with `http_use_ssl` options) was not tried.
